# Сценарный язык CustomOS Visual Novel (черновик v1)

Статус: спецификация этапа 2. Это проектное решение для последующей реализации; пока не означает, что парсер/движок уже доступны в CustomOS.

## 1. Основные правила

- Кодировка исходников: корректный UTF-8. Неполные/некорректные последовательности и встроенный NUL отклоняются с номером строки.
- Имена меток: до 31 байта UTF-8; допускаются Unicode-символы, ASCII-буквы, цифры и `_`, но не пробельные символы или ASCII-пунктуация. Имя должно начинаться с буквы или `_`; в русскоязычном проекте можно писать `label начало:`. Имена чувствительны к регистру и сравниваются по точной UTF-8-последовательности (нормализация Unicode не выполняется).
- Пустые строки игнорируются. Отступы рекомендуются для читабельности, но не являются единственным способом определения структуры.
- В первой версии комментарии начинаются с `#` в начале строки или после пробелов.
- Каждая исполняемая строка заканчивается `;`. Исключения — объявления `label имя:`, `menu:` и заголовки вариантов меню, оканчивающиеся двоеточием.
- Внутри текстовой реплики первый неэкранированный `;` завершает команду; чтобы вывести буквальную точку с запятой, писать `\\;`.
- Строка сценария, не распознанная как поддерживаемая команда, считается репликой только в контексте, где разрешён текст, и при наличии завершающего `;`. Команды из зарезервированного, но неподдерживаемого набора (`call`, `if`, `scene`, `show`, `play` и другие из валидатора) приводят к отдельной ошибке. Для проверки неизвестной директивы существует форма `@имя;`, которая гарантированно выдаёт ошибку неизвестной команды.

## 2. Грамматика на уровне строк

Условная EBNF (терминалы сопоставляются с отдельными непустыми строками исходника):

```ebnf
program       = { blank | comment | label };
label         = "label", identifier, ":", newline,
                { blank | comment | statement };
(* Тело метки продолжается до следующего объявления label на верхнем уровне
   или до конца файла. Переход в следующую метку автоматически не выполняется. *)

statement     = text-line | jump | return | menu;
text-line     = text, ";";
jump          = "jump", identifier, ";";
return        = "return", ";";

menu          = "menu:", newline,
                choice, { choice },
                "endmenu;", newline;
choice        = choice-text, ":", newline,
                { blank | comment | choice-statement },
                "endchoice;", newline;
choice-statement = text-line | jump | return;
identifier    = letter-or-underscore, { letter | digit | "_" };
```

Формальная грамматика дополняется такими ограничениями:

1. `label` объявляется только на верхнем уровне. Объявление с повторным именем — ошибка.
2. `menu:` допускается внутри метки, но не внутри варианта меню в версии 1. Такое вложение выдаёт явную ошибку.
3. `choice-text` — непустая строка текста с удалённым конечным двоеточием. Внутри меню строка, которая не является командой и заканчивается двоеточием, начинает вариант.
4. Каждый вариант обязан содержать хотя бы одну исполняемую команду. Пустые варианты и меню без вариантов — ошибки.
5. Каждый вариант заканчивается отдельной строкой `endchoice;`, а меню — `endmenu;`. Поэтому парсер не зависит только от количества пробелов.
6. Варианты и их последовательности выполняются после выбора. Достигнув `endchoice;` без `jump`/ `return`, исполнитель продолжает команду после `endmenu;`.
7. `jump имя;` немедленно переводит управление в начало метки. Управление не возвращается в исходную ветку.
8. `return;` завершает всю новеллу. Встроенного стека вызовов и команды `call` нет.
9. Достижение конца метки без явного `jump` или `return` также завершает историю; переход к следующей по файлу метке не выполняется автоматически.
10. Синтаксический анализ проходит весь файл до запуска: недостающий `;`, незакрытое меню/вариант, лишний `endchoice;`/ `endmenu;`, команда не в том контексте и неизвестная команда являются ошибками с номером исходной строки.

## 3. Пример корректного сценария

```text
label начало:
    Ты проснулся в неизвестном месте;
    Перед тобой две дороги;
    menu:
        Остаться в городе:
            Ты решил остаться;
            jump город;
        endchoice;
        Отправиться в путешествие:
            Ты решил отправиться в путь;
            jump лес;
        endchoice;
    endmenu;
return;

label город:
    Ты вернулся к привычной жизни;
    return;

label лес:
    Впереди начинается длинная дорога;
    return;
```

## 4. Проверка ошибок

Валидатор должен как минимум сообщать:

- `line N: expected ';' after text` — нет точки с запятой;
- `line N: invalid or unknown command` — неизвестная конструкция;
- `line N: duplicate label 'имя'` — повторная метка;
- `line N: jump target 'имя' does not exist` — несуществующая цель;
- `line N: menu has no choices` — пустое меню;
- `line N: empty choice` — у варианта нет команд;
- `line N: expected endchoice;` — незакрытая ветка;
- `line N: expected endmenu;` — незакрытое меню;
- `line N: menu cannot be nested here` — недопустимая вложенность;
- `line N: empty script` или `no labels defined` — пустой сценарий.

Номера строк относятся к исходному файлу, а не к внутреннему представлению.

## 5. Лимиты первой версии

Лимиты нужно определить константами в общем заголовке движка, чтобы валидатор и редактор использовали одни и те же значения:

- исходный сценарий: не более 48 KiB UTF-8;
- метки: до 128;
- меню: до 16 вариантов;
- инструкции после компиляции: до 4096;
- одна реплика/название варианта: до 512 байт UTF-8;
- итоговый ресурс новеллы: максимум не должен превышать зарезервированную ресурсную область player CBX.

Валидатор обязан отклонять превышение лимита до записи сборки. Не допускаются неограниченные массивы и выделение памяти через libc.

## 6. Формат проекта

На первом этапе хранилище использует плоские имена файлов и постоянный идентификатор проекта (32-битный ID, отображаемый как восемь шестнадцатеричных цифр):

- `P_XXXXXXXX.MET` — метаданные, включая версию формата, ID и отображаемое имя;
- `P_XXXXXXXX.SCR` — исходный UTF-8 сценарий;
- `G_XXXXXXXX.CBX` — последняя успешно собранная игра.

`XXXXXXXX` заменяется фактическим ID. Метаданные и сценарий обновляются независимо, поэтому ошибка компиляции не меняет сборку. Перечисление проектов основывается на валидных файлах метаданных; отсутствующий сценарий должен отображаться как повреждённый проект с сообщением, а не приводить к зависанию редактора.

## 7. Формат внутреннего представления

Промежуточный ресурс имеет сигнатуру `VNB1` и версию формата. Заголовок содержит ID проекта, название, число меток, смещение таблицы меток, смещение/размер области инструкций и общую длину. Все смещения относительны к началу ресурса и проверяются на переполнение и выход за границы.

Минимальный набор инструкций:

- `TEXT` — смещение и длина UTF-8-реплики;
- `JUMP` — индекс существующей метки;
- `RETURN` — завершение;
- `MENU` — список подписей, диапазонов инструкций ветвей и адрес инструкции после меню;
- `CHOICE_END` — завершить текущую ветку меню и продолжить после меню;
- `HALT` — конец текущей метки без перехода к следующей метке.

Внутренний формат не использует адреса памяти хоста и пригоден для включения в CBX. Исполнитель обязан проверять сигнатуру, версию, число инструкций и каждый диапазон ресурса перед использованием. Формат будет считаться стабильным только после реализации тестов парсера и player.

## 8. Порядок для сборки

Редактор сначала запускает валидатор, затем компилирует исходник в `VNB1` в оперативной памяти, далее создаёт новую копию шаблона CBX player и встраивает ресурс в его зарезервированную область. Сборка проверяется до сохранения под именем `G_XXXXXXXX.CBX`. При любой ошибке прежний файл не изменяется.
